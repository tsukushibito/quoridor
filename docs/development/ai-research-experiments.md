# AI研究の実行・再実行・記録

2026-10-02（日本時間）、ユーザーの明示指示により改定。研究タスクの契約・実行・報告に適用する。実行回数を一律一回に制限せず、許可した作業範囲と総予算で管理する。コードと結果の追跡はGit・Beads・必要な実行記録で行う。

## 課題、コード版、実行を分ける

| 単位        | 意味と管理                                                               |
| ----------- | ------------------------------------------------------------------------ |
| 研究課題    | 判別する問いと担当・受入条件。Beadsのissueで管理する                     |
| コード版    | 実行したソース。mainの通常Gitコミットを基本とする                        |
| 実行（run） | あるコード版・設定・入力を使った一回の起動。簡単なrun IDと記録で区別する |
| 評価計画    | 正式な比較の対象・条件・集計・終了規則。設計文書で定義する               |

同じ課題で複数のコード版やrunを扱える。実行ファイルの起動一回を「同じ実験」の上限にしない。バグ修正や確認のたびに別issue・別契約・コード全体のコピーを作る必要はない。問い・所有者・許可範囲が大きく変わる場合に課題や契約を更新する。

## 再実行

- **デバッグ・機能確認**：許可した範囲と総時間・資源予算内で、修正と再実行を反復できる。検査器や設定の不具合も同じ扱い。NNを使う確認も、元の許可範囲と残予算内なら一律禁止しない。
- **再現確認・性能測定**：複数回測定できる。コード版・入力・warmup・測定対象を明確にし、ばらつきを含めて報告する。実行回数の制限が必要なら、予算や測定方法上の具体的理由を示す。
- **正式な棋力比較**：両者のコード・モデル・資源・思考時間・局面・集計方法・終了条件と、エラー時の扱いを結果の前に決める。良い結果だけを採用したり、敗北を無条件に再実行で置き換えたりしない。バグ修正版を測る場合は新しい版の評価として区別し、旧版の結果と無断で統合しない。

許可範囲内のデバッグでは、普通のバグ修正に「原因ごとに一回だけ」「一窓だけ」「NN再試行ゼロ」を標準で課さない。原因が絞れず同じ試行を繰り返す場合は、担当が別案・追加診断・中止を判断する。各runの資源上限・タイムアウト・所有プロセスの停止確認、ユーザーpause、親の期限は守る。

正式評価の不具合では、計画に従って候補側の失敗・参照側の失敗・共通基盤の失敗を区別する。評価として成立しなかった実行を含め、理由を記録する。単なる検査コードの例外を、NNの数値不一致や棋力の敗北という結論へ変換しない。

## 必要な記録だけを残す

通常の実行記録は、issue/run ID、Git版、設定・入力の参照、再現コマンド、開始/終了、成否・必要な結果、エラーの要点とログへの参照で十分とする。seed・モデル・依存版・時間/メモリは、その問いの再現や判断に関係するものを記録する。長時間/非同期ジョブには所有PID等と停止状態も残す。

「失敗を保存する」は、診断と結果の解釈に必要な情報を残す意味である。全ソース・全依存・全過去成果・全メモリ状態を毎回複製する義務ではない。失敗の記録と修正版の結果を区別すれば、失敗したコードを別ディレクトリへ永久保存する必要はない。

コードはmainの通常indexを用いたローカルコミットとして管理し、コミットIDをrunへ結び付ける。失敗や未完成を含むコミットでも、その状態を明記すればよい。未コミットで試す場合は基準コミットと必要な差分、実際に使った未追跡ファイルを記録し、受入れ対象版はGitで特定できるようにする。共有モデル・依存は版/ハッシュと保存先を参照し、runごとにコピーしない。Gitで再現できない生成物・入力・重要な出力だけを必要に応じて別保存する。

正式評価の集計を検証するための棋譜・応答・測定値は保持する。デバッグの大量traceや一時profileは、要点/再現手順を残し、利用中でないことを確認して担当がローテーション・整理できる。既存の成果を本改定だけで一括削除しない。保存容量の上限を守り、不要な複製で失敗ログを増やさない。

## 実験・検証データの保存と整理

実験・検証データは研究Gitの `research-data/ai-sigma/` に保存する。小さい設定・集計・再現manifestは直接保存し、大きい棋譜・応答・測定値・必要なログは課題/run単位の圧縮アーカイブにまとめる。manifestにissue/run、コード版、設定・入力・モデル・環境の参照、アーカイブの内容と展開先を記し、判断に必要な成功・失敗のデータを保持する。結果を書き換えるために旧runを置換しない。Git管理はmain正本へのローカル保存であり、push・公開を含まない。

`.artifacts/ai-sigma/` は実行中の出力・展開用の作業領域とする。停止済みデータはGit保存と復元を確認し、参照している担当が展開先を利用できるようにしてから、不要な元コピーを削除できる。稼働中・検証中のデータを移動や削除で壊さない。過去データも同じ基準で順次整理する。

runの出力先は最初から`.artifacts/`に置き、終了後に必要な集計・manifest・圧縮archiveだけを`research-data/`へ保存する。展開コピーは元pathとSHA・Git版・archive memberの対応で復元できることを確認して撤去する。実行lock、通知の一時状態、描画cacheは保存正本へ混ぜない。未追跡ファイルを一括ignoreして隠すことや、必要な未保存記録を一括削除することは整理の代わりにしない。

コードと記録済み環境から再生成できる実行ファイル・Wasm・ビルドキャッシュ・重複ソースは長期保存しない。未使用と再生成可能性を確認して担当が削除する。未Gitコード、稼働中の運用スクリプト、必要な外部入力・モデル・依存は再取得/再構成できる参照を確保し、必要最低限を共有保持する。Git本体の容量と移管中の一時重複も現在の保存会計に含める。不要な全履歴コピーや別の承認層は追加しない。

## 契約と検証を軽く保つ

既存の設計を契約から参照し、必要な差分・担当・予算・確認条件を記す。通常デバッグに、全履歴の再ハッシュ・全期間資源保証・独立担当による全項目再実行を毎回要求しない。設定/schema/mock等の安い確認を先に行い、修復した最小の動作経路を固定して、主張に必要な独立検証へ渡す。

Rootは新しい原因の発見だけで次の実験を選ばず、結果によって変わる判断、競合案、全工程費で優先度を比較する。重要な方向・データ・学習・モデルの変更は人間へ提示し、通常の修復・再確認は受入れ済み範囲と実予算で担当が進める。独立レビューは前提・主張・採用判断に必要な時だけ依頼する。毎runの全員承認や定期LLM点検を追加しない。

## 現在の研究への適用

本指示は、通常の修正・再確認を妨げる旧一回制限と過剰な複製義務を置き換える。Rootは進行中の契約を差分で整合させ、担当へ有効な許可範囲と残予算を伝える。終了した実行の条件・成績を書き換えたり、既に終了した期限を遡及延長したりしない。

研究コードのローカルGit管理を許可する。共有範囲の書込所有者を守り、研究正本はmainであり、製品機能への統合、push、公開はこの規約では許可しない。CPU/RAM/LLM/GPU/累積容量・現研究枠の期限を拡張しない。タスクの実行指示と現在のジョブ設定にも適用し、文書だけの変更で終えない。

「終了窓の再開」の禁止は、旧実行の期限・成績を遡及的に書き換えないという意味である。同じコード・入力・コマンドでも、現在の許可範囲と総予算内で新runとして再現確認できる。旧.80と同じ内容を新runで検証すること自体は禁止しない。進行中の具体的許可差分と残予算はRootが担当へ明示する。

契約・設計文書の過去版も研究ローカルGit履歴を基本に管理し、修正前全文の別保存を標準にしない。未Git文書は必要な修正前版と現行版を小さく記録する。既に上書きされ、確実な修正前参照を復元できない場合は履歴未記録を明示し、本文を捏造しない。実送信dispatchログは配送証拠として保持する。

## 契約と状態の現行化

研究目標は継続する目標・権限、現行実行枠は現在の期限・上限、担当契約は問い・所有・配分・必要な検証だけを記す。古い禁止事項を残して追記の優先で読み替えず、有効本文を直接更新する。過去条件はGit/実行記録へ参照する。

診断対局と正式認定を分け、普通の診断へ全独立検証・独自proof形式・正式標本数を前提にしない。実行入口の管理は最小のrun種類/版/設定/入力/予算/停止で行い、必要なpause・資源・所有の制御は維持する。

保存上限は現在保持する実量と有効予約の未使用分で管理し、過去peakを別に残す。確認済み未使用予約は解放できる。調査は不支持/不成立/未完了終了でも停止・必要記録・引渡し後にcloseでき、停止・受入れ済みならRootが所有を引き継いでcloseできる。closeだけの新LLM turnや仮説成功は条件にしない。

将来枠は提案できるが別契約作成だけでユーザー指定の終了時刻を解除しない。現在の課題・許可・停止条件はBeadsと担当契約から確認し、必要な読取りと一時障害の有界再試行も実予算に含める。硬い期限・pause・所有不明の拒否を迂回しない。

## 研究コード・設定・データの配置

mainが持続的研究の統合正本で、managed worktreeは並行変更・比較に用いる。現役のコード・指示・文書を旧研究worktreeへ恒常mirrorしない。必要モデル・checkpoint・入力は同volumeの`.worktree/assets/`へ分類し、[`research-paths.json`](../../research-paths.json)でコードと永続資産の参照を分ける。旧checkoutの未保存情報はGit/圧縮記録へ保存して復元を確認し、資産readerの自然停止と移動対応manifestのSHA照合後に撤去する。原runの旧絶対path・SHAは遡及更新しない。現役入口と依存図は[研究コードの保守案内](ai-research-code.md)を参照する。

並行writerはファイル単位で担当を分け、Git index/commitは統合担当一人が操作する。全writerの停止と明示pathを引き渡し、`scripts/dev/research-save.py check`で通常index・既stage・一時物・保存forecastを確認し、Git担当が`save`を実行する。private indexでHEADだけ更新する旧保存helperは将来の標準に使わない。既stage/未保存変更をresetして整合させず、保存失敗時のstageも確認用に保持する。

現役sourceの構文・契約・整形は`python3 scripts/dev/check-research.py`を入口とし、`--format`も対象を限定する。vendor/raw/凍結recipeを全体整形せず、製品buildや科学NNを研究構文検査の前提にしない。source checkpointとruntime/temp/index lockを分け、ローカル一時物を誤ってGit保存しない。

保守タスクの担当は構成と依存境界を利用実態に応じて見直し、README/AGENTS/既手順へ反映する。必要な構造改善は到達構成・保守ルール・段階移行を合わせて定め、同一共通機能のコピーを新しいframeへ増やさない。互換shimは必要なcallerと撤去条件を記録し、二重実装として保守し続けない。定期全体監査・毎run文書更新は義務にしない。

Git履歴修復前のコミットIDが記載された原runの参照は、[旧→新対応表](../../research-data/ai-sigma/263-git-history-repair/commit-map.json)で修復済み履歴へ対応付ける。原runのコード版・科学結果を書き換えない。
