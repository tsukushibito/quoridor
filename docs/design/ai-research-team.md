# タスク単位のAI研究

Rootが人間との窓口、研究状態の整理、作業調整、成果統合を兼ねる。実行担当は必要な仕事ごとに依頼し、独立レビューは前提・実験設計・主張・採用判断に必要な時だけ使う。固定ロール、常設のCoordinator/Supervisor、役割persona、定期LLM点検は設けない。研究は競合仮説と実験から判断を更新し、実装の固定順序へ置き換えない。

## 判断と実行を分ける

人間が到達目標、重要な研究方向、データの選択・規模・分割、学習方式・batch、特徴・モデルの重要な変更を選ぶ。Rootは次の判断に必要な観測、未検証前提、競合案、各案で変わる意思決定と全工程費を示す。LLMの自由な数値採点や実装容易性だけで選ばず、目標への情報価値を比較する。小規模診断の成功を必要なデータ量や別の有力案の恒久的な入口条件にしない。

受入れ済みの仕事、同条件の観測、通常の不具合修復は、担当が有効な範囲・残予算・停止条件で自律的に進める。報告や予算の残りだけでは新しい実験を始めない。独立レビュー担当には問い・事実・対象版を渡し、実行担当の自己評価を採用根拠の代わりにしない。根拠不足、仮説不支持、実験不成立、実装失敗を区別する。

## 研究状態の正本

[研究知見と次の判断](../research-findings.md)へ観測・限界・競合説明・次の人間判断をまとめる。研究報告の正本を分散させず、新しい研究状態DBや別のTODO一覧は作らない。

- 目標と現在の許可範囲への参照。
- 確定した観測とそのコード・入力・結果への参照。
- 未検証前提と競合説明、支持・反証・不明の区別。
- 次の候補、結果によって変わる判断、全工程費と保留理由。
- 次に人間が選ぶ事項。

担当・状態・依存・引渡しは[Beads](../development/beads-workflow.md)、ソース版はGit、測定値・曲線・生データは実験成果物に置く。会話履歴だけを現在の研究状態にせず、同じ情報を複数の台帳へ転記しない。過去の科学記録や会話は現在の許可として扱わない。

## タスクの依頼と並行作業

依頼にはBeads issue、目的と対象外、書込範囲・一人のowner・作業場所、実資源予算、停止条件、受入条件と必要な検証を含める。既存設計と実行規約を参照し、必要な差分だけ渡す。共通の保守・Beads・整形規則はAGENTSと既存手順に置き、担当ごとの常設role定義は作らない。

依存しない実装・解析は並行できる。並行writerはfile/worktree単位で分け、Git index/commitは一人の統合担当だけが操作する。CPU/GPU・RAM・保存・測定競合は実プロセスとタスク予算で判断し、LLMセッションのactive人数を計算資源の使用量に置き換えない。再帰的な委譲をタスク指示だけで許可されたとみなさない。

mainは持続的研究の統合正本。並行変更・具体的な比較にはmanaged worktreeを使う。必要なモデル・checkpoint・入力は同じ永続volumeの`.worktree/assets/`で保持し、指示・文書・現役sourceを恒常mirrorしない。使用中資産と共有DB・lock・worktreeを保護する。[研究コードの保守案内](../development/ai-research-code.md)と[実行・記録規約](../development/ai-research-experiments.md)を参照する。

### 計算枠と直接引渡し

Rootは依存成果物、書込許可、計算許可を分けて配分する。実際の速度比較・profile・対局時計は競合する計算と非重複にする。一方、通常のビルド・NN0ソフト検証は、合計CPU/RAM等が親予算内で、実行中jobが読むbinary/libraryがSHA付きimmutable参照なら並行できる。共有Cargo targetのwriterは常に一人にする。同時実行中のelapsedは全費として残すが、公平な速度比較には使わない。

条件付きの次工程も依頼時に配分し、担当は成果物のbindingと実STOP・childwait・cleanupを次の担当とRootへ直接通知する。既に配分された工程はその条件成立で進め、Rootの受領返答だけを追加gateにしない。開始できない場合は、欠けている具体的な成果物・資源・所有を報告する。終了イベントは既存job通知を使い、確認だけの定期LLM起床や常設調整役を増やさない。

## セッションの選択と再利用

セッションは仕事の継続性と必要なコンテキストで選ぶ。担当を増やすこと自体を目的にせず、Rootは人間との窓口と統合を継続する。

| 作業                                   | 推奨する担当                                                                                                                   |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| 小さな修正、短い確認、人間との判断相談 | Rootで進める。単なる手順分割のために担当を増やさない                                                                           |
| 継続する実装・解析、長時間ジョブ       | 独立した保存セッション。タスクと完了通知を同じthreadへ結び付ける                                                               |
| 短く範囲が限定された調査・並行作業     | 委譲が許可された場合にサブエージェントを使う                                                                                   |
| 重要な結論や変更の独立レビュー         | 実行過程を引き継がない別の保存セッション、または別コンテキストのサブエージェント。継続するレビューは保存セッションを基本にする |

独立性は担当の呼び名やトップレベルのセッションかどうかではなく、実行担当から判断を分離して対象と根拠を確認することで確保する。サブエージェントを使う場合も、必要な契約と書込境界を定める。許可範囲を超える再帰的委譲は行わない。

- 同じ課題の継続、修復、再現確認は既存の担当を再利用する。新しいrunだけを理由に新規セッションを作らない。
- 目的や主要な前提が変わる仕事は新しいセッションにする。独立した再評価にも新しいコンテキストを使い、実行履歴をコピーしたforkを独立性の根拠にしない。
- レビュー指摘の修正確認は同じレビュワーへ戻す。別の問いや前提からの再評価は新しい担当へ渡す。
- 再開時には現在のissue・所有・許可・残予算・停止条件と対象版を確認する。セッションの再利用は新しい実験、予算reset、期限延長、pause解除を許可しない。
- 成果の受入れ・必要な保存と、実行中ジョブ・未処理の完了通知がないことを確認してからアーカイブする。完了した担当を常設ロールとして使い続けない。

## セッションの実行権限

2026-10-06のユーザー指示により、研究の実行担当・独立レビュー担当・サブエージェントは、**作成・再開時に必ずRootと同じフルアクセス権限を設定・確認する**。Rootがフルアクセスでも新しい保存セッションへ自動継承されるとはみなさない。制限付きsandboxを既定のまま使って、読み取りごとの承認待ちやコンテナ内のnamespace起動失敗を繰り返さない。

保存App Server threadは `thread/start` 又は自然idle時の `thread/resume` で `sandbox: "danger-full-access"`、`approvalPolicy: "never"` を明示する。UIを使う場合もFull accessへ揃える。開始元は適用応答のsandbox・approval policyとcwdを確認し、最初の通常コマンドが成功することを確認する。サブエージェントも開始元のフルアクセス設定が引き継がれていることを確認する。モデル・effort・cwdはこの権限整合のために変更しない。

`research-session.sh create/send` とjob完了通知は、承認済みのフルアクセス設定を作成・再開・新turnへ明示する。限定testsの成功と実際の適用応答・通常コマンド成功は区別して確認する。既存セッションがActiveなら通常は自然idleで整合する。起動失敗・承認待ちで実処理が始まっていない場合は、Rootが正確な自分の依頼turnだけを終了し、同じthreadの権限を整合して同じタスクを再開できる。実行中の科学processを権限整合のために無断で中断しない。

フルアクセスはユーザーが指定した実行環境の設定であり、新しい実験・資源上限・書込範囲・削除・公開・重要設計の決定権限を広げない。各タスクの許可、所有、停止条件とRoot経由の人間判断は引き続き守る。この共通設定を毎タスクで再承認する手順は追加しない。

## 渡す情報と担当間の連携

初回依頼にはタスク契約と、現在の事実・未検証前提・対象版・必要な成果物への参照を渡す。Rootの会話全文や実行担当の長い推論履歴を標準で引き継がせず、確認に必要な資料を参照できるようにする。独立レビューには確認する問いと根拠を渡し、実行担当の結論への同意を依頼しない。引渡しは方法、観測結果、不確実性、予想外の事象、成果物参照と停止状態に絞る。

明示された依存関係の入力・出力、修正事項、停止通知は担当間で直接連絡できる。すべての通信をRoot経由にはしない。各通信はissueと対象版を特定し、担当間の合意だけで書込範囲・資源・重要な研究方針を変更しない。それらの変更と人間への判断提示、成果の採否・統合保存はRootへ戻す。結果待ちは既存の通知経路を使い、進捗確認だけのLLM turnを繰り返さない。

## 独立レビューを適用する条件

Rootが次の条件に照らして、タスク依頼時にレビュー対象・依頼条件・範囲・予算を定める。その範囲では実行担当が必要な時点で直接独立レビューを依頼し、通常修正と指摘の確認を同じレビュワーと進める。Rootによる定期監視や、レビュー起動ごとの承認を入口にしない。指定されていない重要な研究結論、想定外の矛盾、レビュー要否が曖昧な問題、設計・範囲・予算変更はRootへ戻す。人間はこの運用方針と重要な研究方向を選び、通常のタスク分類を毎回承認する役にはしない。

| 独立レビューが必要な場面                                                                     | 確認する対象                                   |
| -------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| 棋力改善、原因特定、方式の優位性など重要な研究結論を採用する                                 | 比較条件、指標、集計、不確実性、結論の適用範囲 |
| 分割・漏洩対策、ラベルの視点、入力変換・特徴、評価器・探索の変更が広く結果の妥当性を左右する | 変更した境界、前提、対応する正しさと検証の不足 |
| Gitで復旧できない必要データやモデルを削除・置換する                                          | 利用者、必要性、保全・復元可能性、操作対象     |

該当条件をRoot自身の「低リスク」という感覚だけで免除しない。判断が曖昧な場合は対象を絞って確認し、重要な方針変更や許可の不足だけを人間へ提示する。独立レビューを確保できない間は該当する採用・操作を保留し、影響しない作業は進められる。

レビューは導入・採用時の関連差分と根拠へ限定し、毎runに繰り返さない。通常の文書・整形、既知の不具合修復、資格済みの変更していない手順による生成・学習、同条件の再実行は担当の検証とRootの受入れを基本とする。ただし説明できない矛盾や予想外の挙動が出た場合は、その点を対象にレビューする。修復でも上記条件に該当する変更は独立レビューへ回す。

レビュワーには問い・仕様・元資料・対象版/差分・検証結果を渡し、実行担当の長い推論履歴を標準で引き継がせない。結果は実行担当とRootへ渡す。Rootは採用時に必要な境界の確認と重大な未解決指摘の有無を確認し、レビューの全作業を再実行しない。常設レビュワーや全変更のレビューは設けず、必要な対象の完了後に区切る。

機械的な正しさには独立oracleや自動検査を活用し、同じ検査を別LLMに反復させることを必須にしない。自動検査が覆わない前提・解釈・結論は別担当または人間が確認する。Rootや実行担当の自己レビューだけでは独立レビューを満たさず、人間の単なる実行承認も内容の確認とは区別する。確認した範囲と根拠は既存issueや受入れ記録に残すが、全タスク共通の採点表、レビュー不要報告、全員承認は追加しない。

## タスク用セッションの通信

`scripts/dev/research-session.sh`は既存App Serverへの単発クライアント。新規タスクを作る時はissueと依頼本文、既存担当へ送る時は保存thread IDとissueを明示する。role registryは使わず、App Serverの起動・再起動や定期LLMサービスは追加しない。

作成・再開には上記の[実行権限の設定・確認](#セッションの実行権限)も適用する。下記クライアントの受付と実行権限の適用を区別する。

```bash
# 新しい担当のタスクを直接開始する。準備だけの常設role turnは作らない
bash scripts/dev/research-session.sh create \
  --issue <task-issue> --body-file /absolute/path/task.md \
  --cwd /workspaces/quoridor/.worktree/<managed-name>

# 既存の担当へ依頼。activeなら現在の正確turnへsteer、idleならstart
bash scripts/dev/research-session.sh send \
  --thread <thread-id> --issue <task-issue> \
  --body-file /absolute/path/task.md --cwd /workspaces/quoridor

bash scripts/dev/research-session.sh status --thread <thread-id>
bash scripts/dev/research-session.sh read --thread <thread-id> --limit 1
bash scripts/dev/research-session.sh wait --thread <thread-id> --timeout 45
# 受入れ・保存と、ジョブ・未処理の完了通知がないことを確認してから
# active threadはarchiveできない
bash scripts/dev/research-session.sh archive --thread <thread-id>
```

クライアントはissueの状態・pauseと、send直前の`codex:<thread-id>`の担当一致を確認する。createは未担当または操作元が所有するissueだけを受け、担当・状態のCAS確認付きで新threadへ移譲してから実タスクを開始する。報告も宛先が所有するissueを指定する。担当が変わった場合は誤配せず、作成後の失敗はthread IDを残して再作成を自動反復しない。報告やready状態をpause解除として扱わない。activeへのsteerはcwd移動と別で、配置変更は自然idle後の新しい依頼で行う。モデル・effortはホストの現在設定を使い、追加依頼で無断変更しない。タスク固有の追加指示は`create --instructions-file`で渡せるが、恒常role promptとして複製しない。

依存は`tools/research-session/pyproject.toml`と`uv.lock`に保持する。専用環境は共有学習環境へ混ぜない。既存専用環境の物理pathは移行で作り直さず、`QUORIDOR_RESEARCH_SESSION_ENV`で指定できる。依存準備済みで同期を行わない操作は`UV_NO_SYNC=1 UV_OFFLINE=1 PYTHONDONTWRITEBYTECODE=1`を付ける。

## 長時間ジョブと終了

計算の開始、資源制御、上限付きログ、取消、所有プロセスの回収、完了通知は[ジョブ運用](../development/research-jobs.md)のコードへ渡す。担当はjob IDと結果参照を残してturnを終了できる。完了まで周期的なLLM確認をしない。通知は既存の担当threadへ一度だけ届け、別の監督LLMを起こさない。

枠やタスクの終了では、担当が実処理・writerの停止、必要な記録、未完了事項、次の再開条件を引き渡す。Rootは受入れと統合保存、Beadsの状態とbackupを確認する。終了時に全員を起こす手順や全役の承認待ちは設けない。保守・整理は構成変化と利用実態から要否を判断し、必要な場合だけ別タスクの範囲・担当・時期を決める。未完了を理由に期限や許可を自動延長しない。

旧固定チームの履歴、必要な科学記録・モデル・入力は保持する。旧role名や終了済み契約は過去記録であり、現役の依頼先や実行許可には使わない。現在の作業は明示threadとBeads issueに結び付ける。
