# タスク単位のAI研究

2026-10-07の人間の指示により、方針相談担当（Root、この会話）と実行・統合担当（別の保存セッション）を分ける。方針の壁打ちを、長い統合作業やワーカーの通常報告で中断させない。タスク別ワーカーと必要な独立レビュアーは従来通り再用し、監視専用セッション、役割persona、定期LLM点検は追加しない。研究は競合仮説と実験から判断を更新し、実装の固定順序へ置き換えない。

| 担当                 | 責務・所有                                                                                                                                                      |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 方針相談担当（Root） | 人間との壁打ち、結果の解釈・選択肢・全工程費の提示、重要な研究方向と許可範囲の記録。研究epicを所有する。main/Gitは書かない。                                    |
| 実行・統合担当       | 許可済み仕事の依頼・順序・資源調整、報告回収、関連レビュー、成果の採否・検証・main統合。実行・統合issueとmain/Git/index、研究知見文書のwriterを一人で所有する。 |
| タスク別ワーカー     | 指定worktree・範囲で実装/計測/解析。自身のissueとジョブ通知先は維持し、通常報告は実行・統合担当へ渡す。                                                         |
| 独立レビュアー       | 必要な採用境界だけを独立確認し、修復は同じ担当が関連確認する。実行・統合担当へ報告する。                                                                        |

担当の具体的thread ID・issueはBeadsの現在の担当と依頼に結び付け、別のrole registryや並行した研究状態台帳は作らない。実行・統合セッションは実際の引渡し・統合作業から開始し、完了通知や具体依頼がない間はIdleにする。

### 現行資源方針（2026-10-08、人間採択）

[将来工程のtyped支持](../../research-data/ai-sigma/execution-resources-20261008.json)を現行とする。保存上限は50GB＝50,000,000,000B（約46.57GiB）。従前12.5GiB＋追加512MiBとCPU4/RAM8GiB/VRAM6GiBは過去の使用済み契約として保持し、今後の配分上限には使わない。CPU・RAM・VRAMは実際の空き容量、安全なjob peak、thread/worker上限で制御する。空き容量をすべて同時jobへ渡さず、科学的なbatch・モデル・探索仕事量は変更しない。

速度比較・perf・時間制御対局・明示的なtiming診断は共有hardware上で直列にし、計測中は substantial build、学習/GPU、CPU解析、ブラウザ検証、大きなdisk IOを止める。CPU affinityの分離だけではcache・memory bandwidth・power/thermal・diskの干渉を防げない。軽いsource/metadata準備は継続でき、計測外の通常build/test/reviewは実資源と独立writer/immutable入力が成立すれば並行できる。sole共有Cargo writerとsole main/Git writerは維持する。

支持は承認済み各工程のsource、build/link、private、raw、関連review、Git、失敗とcleanupを含むwhole phaseへ一括配分する。個々の小ファイル増分に再承認を要求しない。旧job/proof/cap/failure費は変更せず、未来entryで新proofと実source/private/physics/quietを束縛する。323 USERPAUSE、封印、固定モデル/default、研究方法の判断境界は変えない。

不要な再構築可能cache・旧未使用ELF・obsolete worktree・重複working copyは、復元確認・unique未保存内容・実reader STOPを確認して指定範囲だけ除去できる。固有の科学データ・必要model/input・圧縮した原因/来歴/失敗証拠・Git/archive復元元・Beads/locksを保護する。過去peak/予約は記録として保持するが、現在retentionと終了した一時寿命が証明された後も重複して永久加算しない。同inodeは一度、実証済み直列TMPは最大寿命で数える。UNKNOWNを根拠なしにzeroへ変えず、全体auditを次工程のgateにしない。

## 方針相談への通知

ジョブの完了イベントは元のワーカーへ届ける。START/STOP、通常の修復、詳細ログ、少額の保存再分類などの通常報告は実行・統合担当へ届け、方針相談の会話へ毎回転送しない。担当間の必要なSTOP/依存通知は直接連絡する。

方針相談へ送るのは、人間の判断が必要な許可外変更・重大な矛盾、相談中の問いに直接答える結果、人間が求めた成果要約に絞る。「結果・限界・次の判断・根拠リンク」の短い引渡しを使う。通常成果は既存の研究知見とBeadsへ保存し、相談の区切りや状況確認で参照する。緊急のpause/cancelは遅らせない。通常作業に毎回の人間/相談担当ACKを追加しない。

### 構成変更時の引渡し

全ワーカーの完了待ちは不要。実行中ジョブのissue所有・worker thread・固定config・完了通知先は変更せず、結果回収後の報告先だけを新しい実行・統合担当へ切り替える。main/Gitの旧writerは変更と必要保存を完了してSTOPし、新担当へ一度引き渡す。読み手がいる対象sourceの変更はそのreaderSTOPを待つ。既に送信した旧宛の遅延報告は移管時の残件として一度引き渡し、ジョブ再実行・pause解除・旧issueの起床を行わない。

## 判断と実行を分ける

人間が到達目標、重要な研究方向、データの選択・規模・分割、学習方式・batch、特徴・モデルの重要な変更を選ぶ。Rootは次の判断に必要な観測、未検証前提、競合案、各案で変わる意思決定と全工程費を示す。LLMの自由な数値採点や実装容易性だけで選ばず、目標への情報価値を比較する。小規模診断の成功を必要なデータ量や別の有力案の恒久的な入口条件にしない。

受入れ済みの仕事、同条件の観測、通常の不具合修復は、担当が有効な範囲・残予算・停止条件で自律的に進める。報告や予算の残りだけでは新しい実験を始めない。独立レビュー担当には問い・事実・対象版を渡し、実行担当の自己評価を採用根拠の代わりにしない。根拠不足、仮説不支持、実験不成立、実装失敗を区別する。

## タスクの依頼と並行作業

依頼にはBeads issue、目的と対象外、書込範囲・一人のowner・作業場所、実資源予算、停止条件、受入条件と必要な検証を含める。既存設計と実行規約を参照し、必要な差分だけ渡す。共通の保守・Beads・整形規則はAGENTSと既存手順に置き、担当ごとの常設role定義は作らない。

依存しない実装・解析は並行できる。並行writerはfile/worktree単位で分け、Git index/commitは一人の統合担当だけが操作する。CPU/GPU・RAM・保存・測定競合は実プロセスとタスク予算で判断し、LLMセッションのactive人数を計算資源の使用量に置き換えない。再帰的な委譲をタスク指示だけで許可されたとみなさない。

mainは持続的研究の統合正本。並行変更・具体的な比較にはmanaged worktreeを使う。必要なモデル・checkpoint・入力は同じ永続volumeの`.worktree/assets/`で保持し、指示・文書・現役sourceを恒常mirrorしない。使用中資産と共有DB・lock・worktreeを保護する。[研究コードの保守案内](../development/ai-research-code.md)と[実行・記録規約](../development/ai-research-experiments.md)を参照する。

### 計算枠と直接引渡し

実行・統合担当は、人間が許可した親枠の中で依存成果物、書込許可、計算許可を分けて配分する。実際の速度比較・profile・対局時計は競合する計算と非重複にする。一方、通常のビルド・NN0ソフト検証は、合計CPU/RAM等が親予算内で、実行中jobが読むbinary/libraryがSHA付きimmutable参照なら並行できる。共有Cargo targetのwriterは常に一人にする。同時実行中のelapsedは全費として残すが、公平な速度比較には使わない。

条件付きの次工程も依頼時に配分し、担当は成果物のbindingと実STOP・childwait・cleanupを次の担当と実行・統合担当へ直接通知する。既に配分された工程はその条件成立で進め、実行・統合担当の受領返答だけを追加gateにしない。開始できない場合は、欠けている具体的な成果物・資源・所有を報告する。終了イベントは既存job通知を使い、確認だけの定期LLM起床や常設調整役を増やさない。

2026-10-08の人間の明示指示で、短期補助を同時に最大2件とする従前の制限を撤廃した。[現行の前向き運用overlay](../../research-data/ai-sigma/execution-auxiliary-policy-20261008.json)が、SHA固定した資源証明の旧人数fieldだけを上書きする。容量配分と過去jobの証拠は変更しない。別の固定人数上限は設けない。独立して必要な受入れ・source・依存確認がある場合に、実資源、immutable入力とread/write所有権、期待する調整費から並行数を決める。適した空き保存セッションを再用し、必要なら具体的な有界タスクの新規セッションを作れる。常設役割、定期監視、重複する科学レビュー、不要な全履歴監査は増やさない。

各補助はBeads leaf、限定path・問い・出力・writer、支持されたwhole資源予測・STOP・検証を持つ。main/Git/index・最終採用・資源承認は実行・統合担当に留め、通常検証の実行はタスクに明示して配分する。実計測中のsubstantial compute/IOは停止を待ち、supplied成功証拠を担当を埋めるために再実行しない。作成・再開時にdanger-full-access/approvalPolicy neverを明示し、適用されたmodel/effort/cwdと実turn_contextを通常command前に確認する。過去の最大2件計画と使用済み契約は履歴として保持するが、現行の依頼には人数gateとして適用しない。50GB、sole共有Cargo writer、fairclock、研究方法の承認境界、323 USERPAUSE・封印・model/defaultは変えない。

各phaseのsource/control/runtime/log・必要な関連review・統合分とbounded overheadを一つのinclusive予測へまとめ、支持された上限内の個々のファイルを受領返信待ちにしない。未配分枠は実行・統合担当が根拠つきで配分し、actual資産・旧失敗費・buildUNKNOWNを返金しない。修復担当は指定された問い・予算内で同レビュアーへ固定版と検証を直接渡し、blocker解消・実readerSTOPを受けて次の条件付き工程へ進む。source/private版・resource proof変更は明示し、機械検査で全条件を満たしても追加の324/human ACKを要求しない。実行・統合担当は最終bundleと新たな不足・矛盾を受け取り、同じSHA全検査や独立レビューを重ねず、変更境界と重大未解決指摘を確認する。Cargo writerと公平な数値時計の直列化、未配分工程・pause・封印境界は維持する。

人間が不在中の自律配分を明示承認した場合も、次回確認日は科学jobの強制停止期限にしない。意味ある完了/依存待ちのイベントで、他担当の解除、近い成果の検証・統合、承認済み実装・有限計測、次判断の設計調査の順に有用で実行可能な仕事を選ぶ。同価値なら全費が小さく実CPU/RAM/保存/所有が成立する候補を選び、具体issueと同保存担当へ直接渡す。先行工程が未準備なら未予約slotを状態名だけで保持せず、実ready工程を調整する。実予約・jobは正確STOPまで保護し、mainへの実採否/version引渡しや固定入力・実readerSTOPという必要依存を残す。新method/モデル/特徴/学習条件はこの配分から自動承認しない。実行可能な有用候補がない時だけ具体理由をBeadsへ残してIdleにし、周期LLM監督や翌日要約の自動起床を作らない。

過去契約である2026-10-07の承認済み[前向き配分](../../research-data/ai-sigma/execution-autonomy-20261007.json)は親保存12.5GiB/13,421,772,800B、追加512MiBだけを対象とする。旧予約・assets/failed費/buildUNKNOWN/UNKNOWN128MiBは保持し、新entryにだけtyped proofとwhole-phase forecastを束縛する。実行担当はこの追加内の支持された分類を人間の再返信なしに調整できる。CPU4/RAM8GiB/VRAM6GiBは維持し、一つの公平時計とsole Cargo writerを実processで守る。対象工程の容量超過・重要な新methodや矛盾はその工程を止めて人間向け選択肢を残し、他の承認済み仕事は継続する。

## セッションの選択と再利用

セッションは仕事の継続性と必要なコンテキストで選ぶ。担当を増やすこと自体を目的にせず、方針相談と実行・統合の二系統を維持する。実行・統合の継続は同じ保存セッションで扱う。

| 作業                                   | 推奨する担当                                                                                                                   |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| 小さな修正、短い確認、人間との判断相談 | 方針相談はRoot、source修正・統合確認は実行・統合担当で進める。単なる手順分割で担当を増やさない                                 |
| 継続する実装・解析、長時間ジョブ       | 独立した保存セッション。タスクと完了通知を同じthreadへ結び付ける                                                               |
| 短く範囲が限定された調査・並行作業     | 委譲が許可された場合にサブエージェントを使う                                                                                   |
| 重要な結論や変更の独立レビュー         | 実行過程を引き継がない別の保存セッション、または別コンテキストのサブエージェント。継続するレビューは保存セッションを基本にする |

独立性は担当の呼び名やトップレベルのセッションかどうかではなく、実行担当から判断を分離して対象と根拠を確認することで確保する。サブエージェントを使う場合も、必要な契約と書込境界を定める。許可範囲を超える再帰的委譲は行わない。

- 同じ課題の継続、修復、再現確認は既存の担当を再利用する。新しいrunだけを理由に新規セッションを作らない。
- 目的や主要な前提が変わる仕事は新しいセッションにする。独立した再評価にも新しいコンテキストを使い、実行履歴をコピーしたforkを独立性の根拠にしない。
- レビュー指摘の修正確認は同じレビュワーへ戻す。別の問いや前提からの再評価は新しい担当へ渡す。
- 再開時には現在のissue・所有・許可・残予算・停止条件と対象版を確認する。セッションの再利用は新しい実験、予算reset、期限延長、pause解除を許可しない。
- 成果の受入れ・必要な保存と、実行中ジョブ・未処理の完了通知がないことを確認してからアーカイブする。完了したタスク担当を監視役として起床しない。方針相談/実行・統合の継続セッションも、具体依頼・完了通知がなければIdleにする。

## セッションの実行権限

2026-10-06のユーザー指示により、研究の実行担当・独立レビュー担当・サブエージェントは、**作成・再開時に必ずRootと同じフルアクセス権限を設定・確認する**。Rootがフルアクセスでも新しい保存セッションへ自動継承されるとはみなさない。制限付きsandboxを既定のまま使って、読み取りごとの承認待ちやコンテナ内のnamespace起動失敗を繰り返さない。

保存App Server threadは `thread/start` 又は自然idle時の `thread/resume` で `sandbox: "danger-full-access"`、`approvalPolicy: "never"` を明示する。UIを使う場合もFull accessへ揃える。開始元は適用応答のsandbox・approval policyとcwdを確認し、最初の通常コマンドが成功することを確認する。サブエージェントも開始元のフルアクセス設定が引き継がれていることを確認する。モデル・effort・cwdはこの権限整合のために変更しない。

`research-session.sh create/send` とjob完了通知は、承認済みのフルアクセス設定を作成・再開・新turnへ明示する。限定testsの成功と実際の適用応答・通常コマンド成功は区別して確認する。既存セッションがActiveなら通常は自然idleで整合する。起動失敗・承認待ちで実処理が始まっていない場合は、Rootが正確な自分の依頼turnだけを終了し、同じthreadの権限を整合して同じタスクを再開できる。実行中の科学processを権限整合のために無断で中断しない。

フルアクセスはユーザーが指定した実行環境の設定であり、新しい実験・資源上限・書込範囲・削除・公開・重要設計の決定権限を広げない。各タスクの許可、所有、停止条件とRoot経由の人間判断は引き続き守る。この共通設定を毎タスクで再承認する手順は追加しない。

## 渡す情報と担当間の連携

初回依頼にはタスク契約と、現在の事実・未検証前提・対象版・必要な成果物への参照を渡す。Rootの会話全文や実行担当の長い推論履歴を標準で引き継がせず、確認に必要な資料を参照できるようにする。独立レビューには確認する問いと根拠を渡し、実行担当の結論への同意を依頼しない。引渡しは方法、観測結果、不確実性、予想外の事象、成果物参照と停止状態に絞る。

明示された依存関係の入力・出力、修正事項、停止通知は担当間で直接連絡できる。すべての通信を方針相談担当経由にはしない。各通信はissueと対象版を特定し、担当間の合意だけで書込範囲・資源・重要な研究方針を変更しない。それらの変更と人間への判断提示、成果の採否・統合保存は実行・統合担当へ戻す。重要な研究方針・許可の変更だけをRoot経由で人間へ提示する。結果待ちは既存の通知経路を使い、進捗確認だけのLLM turnを繰り返さない。

## 独立レビューを適用する条件

実行・統合担当が次の条件に照らして、許可済みタスク依頼時にレビュー対象・依頼条件・範囲・予算を定める。その範囲では実行担当が必要な時点で直接独立レビューを依頼し、通常修正と指摘の確認を同じレビュワーと進める。定期監視や、レビュー起動ごとの相談担当承認を入口にしない。指定されていない重要な研究結論、想定外の矛盾、レビュー要否が曖昧な問題、設計・範囲・予算変更はRootへ戻す。人間はこの運用方針と重要な研究方向を選び、通常のタスク分類を毎回承認する役にはしない。

| 独立レビューが必要な場面                                                                     | 確認する対象                                   |
| -------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| 棋力改善、原因特定、方式の優位性など重要な研究結論を採用する                                 | 比較条件、指標、集計、不確実性、結論の適用範囲 |
| 分割・漏洩対策、ラベルの視点、入力変換・特徴、評価器・探索の変更が広く結果の妥当性を左右する | 変更した境界、前提、対応する正しさと検証の不足 |
| Gitで復旧できない必要データやモデルを削除・置換する                                          | 利用者、必要性、保全・復元可能性、操作対象     |

該当条件を実行・統合担当自身の「低リスク」という感覚だけで免除しない。判断が曖昧な場合は対象を絞って確認し、重要な方針変更や許可の不足だけを人間へ提示する。独立レビューを確保できない間は該当する採用・操作を保留し、影響しない作業は進められる。

レビューは導入・採用時の関連差分と根拠へ限定し、毎runに繰り返さない。通常の文書・整形、既知の不具合修復、資格済みの変更していない手順による生成・学習、同条件の再実行は担当の検証と実行・統合担当の受入れを基本とする。ただし説明できない矛盾や予想外の挙動が出た場合は、その点を対象にレビューする。修復でも上記条件に該当する変更は独立レビューへ回す。

レビュワーには問い・仕様・元資料・対象版/差分・検証結果を渡し、実行担当の長い推論履歴を標準で引き継がせない。結果は実行担当と実行・統合担当へ渡す。実行・統合担当は採用時に必要な境界の確認と重大な未解決指摘の有無を確認し、レビューの全作業を再実行しない。常設レビュワーや全変更のレビューは設けず、必要な対象の完了後に区切る。

機械的な正しさには独立oracleや自動検査を活用し、同じ検査を別LLMに反復させることを必須にしない。自動検査が覆わない前提・解釈・結論は別担当または人間が確認する。実行・統合担当や実行担当の自己レビューだけでは独立レビューを満たさず、人間の単なる実行承認も内容の確認とは区別する。確認した範囲と根拠は既存issueや受入れ記録に残すが、全タスク共通の採点表、レビュー不要報告、全員承認は追加しない。

## タスク用セッションの通信

`scripts/dev/research-session.sh`は既存App Serverへの単発クライアント。新規タスクを作る時はissueと依頼本文、既存担当へ送る時は保存thread IDとissueを明示する。role registryは使わず、App Serverの起動・再起動や定期LLMサービスは追加しない。

2026-10-09の人間指示による限定例外として、`quoridor-4lc.352` の15分ごとの軽量運用健全性チェックを許可する。周期処理はcodeと有界metadataの読み取りだけで、各回にLLMを起こさない。新しい問題候補の判断担当は既存の方針相談Root（thread `01a0f2e9-357d-7ef3-a2fe-b16f80accda5`、epic `quoridor-4lc`）。初期状態は相談モードで、検出と小さな重複抑制・保留参照の保存だけを行い、Rootや実行・統合を自動で起こさない。人間が明示して自律確認モードへ切り替えた場合だけ、保留候補の現状を再検証し、Rootがidleになる自然な境界で必要な候補を一度に通知する。Activeな相談や実行・統合を周期steerしない。既に修復・進行が始まった候補は保留から除く。チェック停止は周期検出とmonitor通知を止め、保留と設定を保持する。モードは再起動後も保持し、沈黙や経過時間で切り替えない。

方針相談が必要性を判断して、既承認の具体的な修復・担当変更だけを実行・統合へ渡す。通常workerの結果・job完了・Sigma actualSTART通知は既存のevent経路を維持する。チェックは科学jobをkill・再起動せず、pause解除・N選択・新実験・権限拡大も行わない。保存・起動・停止とコンテナの存続条件は[ジョブ運用](../development/research-jobs.md)の限定例外を参照する。この例外は新しい常設LLM役や全タスクの必須監査を作らない。

作成・再開には上記の[実行権限の設定・確認](#セッションの実行権限)も適用する。下記クライアントの受付と実行権限の適用を区別する。

```bash
# 新しい担当のタスクを直接開始する。準備だけの常設role turnは作らない
bash scripts/dev/research-session.sh create \
  --issue <task-issue> --body-file /absolute/path/task.md \
  --cwd /workspaces/quoridor/.worktree/<managed-name>

# 既存の担当へ依頼。activeなら現在の正確turnへsteer、idleならstart
bash scripts/dev/research-session.sh send \
  --thread <thread-id> --issue <task-issue> \
  --body-file /absolute/path/task.md --cwd /workspaces/quoridor

bash scripts/dev/research-session.sh status --thread <thread-id>
bash scripts/dev/research-session.sh read --thread <thread-id> --limit 1
bash scripts/dev/research-session.sh wait --thread <thread-id> --timeout 45
# 受入れ・保存と、ジョブ・未処理の完了通知がないことを確認してから
# active threadはarchiveできない
bash scripts/dev/research-session.sh archive --thread <thread-id>
```

クライアントはissueの状態・pauseと、send直前の`codex:<thread-id>`の担当一致を確認する。createは未担当または操作元が所有するissueだけを受け、担当・状態のCAS確認付きで新threadへ移譲してから実タスクを開始する。報告も宛先が所有するissueを指定する。担当が変わった場合は誤配せず、作成後の失敗はthread IDを残して再作成を自動反復しない。報告やready状態をpause解除として扱わない。activeへのsteerはcwd移動と別で、配置変更は自然idle後の新しい依頼で行う。モデル・effortはホストの現在設定を使い、追加依頼で無断変更しない。タスク固有の追加指示は`create --instructions-file`で渡せるが、恒常role promptとして複製しない。

依存は`tools/research-session/pyproject.toml`と`uv.lock`に保持する。専用環境は共有学習環境へ混ぜない。既存専用環境の物理pathは移行で作り直さず、`QUORIDOR_RESEARCH_SESSION_ENV`で指定できる。依存準備済みで同期を行わない操作は`UV_NO_SYNC=1 UV_OFFLINE=1 PYTHONDONTWRITEBYTECODE=1`を付ける。

### Desktop と CLI で同じ保存セッションを開く

既存の Desktop App Server に接続する場合は、project cwd で次を使う。

```bash
codex agents --disable api_key_model_discovery
codex resume <thread-id> --disable api_key_model_discovery
```

2026-10-08 の実測では CLI と実行中 Desktop server はともに 0.161.0。
Desktop の `config/read` は `api_key_model_discovery=false`、CLI の既定は
true だった。起動時だけ `--disable` を指定すると、`agents` は既存の
11 task を表示し、選択と明示 ID の `resume` の両方で実行中 policy thread
の履歴と現在 turn を同じ title/model/full-access のまま表示した。
`Ctrl+D` は両 CLI を exit0 で detach し、進行中の仕事は続いた。

この接続では `--no-daemon` を付けない。先の bypass 案より、同じ server
への実測済み接続を使う。非対応 terminal では `TERM=xterm-256color`、
表示には `--no-alt-screen` を起動時に足せる。server feature の変更、
再起動、再認証、global config への永続設定はこの修復に含めない。
managed package の 0.159.2 は実行中 server の版ではなく、原因と扱わない。

その後、人間が `~/.codex/config.toml` の `[features]` に
`api_key_model_discovery=false` を明示保存し、CLI の effective false と
同じ Desktop 接続の成功を確認した。既定値が一致する間は上の起動時 override は
不要だが有効であり、この設定を実行担当が再書込する必要はない。
server0.161.0 は再起動していない。先の起動時限定の実測は履歴として保持する。

確認済みなのは live attachment/history streaming と detach まで。
CLI からの user-message、queue delivery、turn-start、cancel/interrupt の
双方向動作は未検証で、新しい model call も発生させていない。
既存 `research-session.sh` の read/steer/start は同じ backend を使い、
担当・permission・Beads・資源の境界を引き続き守る。
[実測の受入れ範囲と資源](../../research-data/research-session-desktop-cli-attachment.json)
を参照する。[公式 CLI 文書](https://learn.chatgpt.com/docs/developer-commands?surface=cli#codex-resume)
の session-ID resume と、この環境の feature handshake の実測を区別する。

## 長時間ジョブと終了

計算の開始、資源制御、上限付きログ、取消、所有プロセスの回収、完了通知は[ジョブ運用](../development/research-jobs.md)のコードへ渡す。担当はjob IDと結果参照を残してturnを終了できる。完了まで周期的なLLM確認をしない。通知は既存の担当threadへ一度だけ届け、別の監督LLMを起こさない。

枠やタスクの終了では、担当が実処理・writerの停止、必要な記録、未完了事項、次の再開条件を引き渡す。実行・統合担当は受入れと統合保存、Beadsの状態とbackupを確認する。終了時に全員を起こす手順や全役の承認待ちは設けない。保守・整理は構成変化と利用実態から要否を判断し、必要な場合だけ別タスクの範囲・担当・時期を決める。未完了を理由に期限や許可を自動延長しない。

旧固定チームの履歴、必要な科学記録・モデル・入力は保持する。旧role名や終了済み契約は過去記録であり、現役の依頼先や実行許可には使わない。現在の作業は明示threadとBeads issueに結び付ける。
