# 実行基盤との契約

改訂: 能力調査・通知方針 v2（2026-09-29）

このSkillは委譲と受入れの判断を定める。スレッドの起動、通知、再開、状態の保存は、そのセッションを管理するホストの実機能を使う。Leadの再開にはApp Serverの既存スレッドへのメッセージ送信機能を優先する。特定版のApp Server、ソケット位置、独自の常駐プロセスをSkillの前提にしない。

## 毎回の能力確認

利用中のホストが公開するツールと、そのホストで実際に動くApp Serverのスキーマを確認する。CLIと稼働中サーバーが同じ版とは仮定しない。メソッド名や引数は過去の会話やこの文書から推測せず、現行スキーマまたは公式資料と照合する。

### 調べ方の方針

- **接続先を特定する。** ホストが提供するセッション情報、環境情報、CLIのヘルプや状態表示を手掛かりに、元Leadのスレッドと、それを管理する実行基盤への接続方法を調べる。接続先や通信方式を既知のパスから決め打ちしない。別サーバーの新規起動だけでは、元ホストの能力確認にならない。
- **公開インターフェースをたどる。** 専用ツールが見当たらなければ、CLI、App Serverなどの公開APIで同じ能力を利用できるか調べる。稼働中の実装に対応するスキーマ、ヘルプ、公式資料を照合し、引数・応答・通知・接続方式を確認する。ツール一覧にないことを機能不足の根拠にしない。
- **読み取りから確認する。** スレッド情報、設定、状態、モデル一覧など、必要な情報に絞って接続と応答を確かめる。設定保持は、既存スレッドの設定を上書きせず継承できるかを確認する。値の読み出し・再指定を一律の必須手順にせず、取得できた設定値は診断・記録に使う。設定値と実際の各ターンの実行計測は区別する。
- **既存のメッセージ経路を使う。** Sidekickから元Leadのスレッドを宛先に報告を送れるか調べる。受信時のターン開始・実行中入力の扱いはホストの仕様で確認し、その機能を使う。独自の通知サービス、配送キュー、重複排除機構を一律の前提にしない。元Leadへの試験入力はターンを開始・中断し得るため、読み取り診断とは分けて扱う。
- **証拠と未確認事項を残す。** 接続先、実装の版、参照元、確認結果を記録する。同じ接続先・版・構成で有効な検証結果は再利用し、変更の影響する部分を再確認する。未調査、API非対応、接続処理の未整備、動作未検証を区別し、未確認のまま成功を報告しない。

### 必要な能力

| 能力 | 確認すること |
|---|---|
| Lead識別 | 元のホストとLeadスレッドIDを信頼できる情報から取得できる |
| 設定保持 | 再開時点のLeadのモデル・エフォートをホストの継承動作で保持でき、Sidekick用設定と分離できる |
| Sidekick起動 | 許可済みモデルとエフォート、Sidekick方針、今回の契約を省略せず渡せる |
| 通知と再開 | Leadのターン終了後も、Sidekickから元スレッドへメッセージを送り、Leadの次のターンを開始できる |
| 状態と所有権 | Leadの実行中・別作業中・キャンセル済み状態と、Sidekickの書き込み停止を確認できる |
| 記録と異常確認 | ホストの履歴やタスク記録に報告・試行・受入状態を残し、実行状態から失敗・中断を成功と区別できる |
| 計測 | 取得可能な使用量と時刻をLeadへの定期的なモデル入力なしで記録できる |

App Serverのメッセージ送信機能で元Leadへ報告してターンを開始できるなら、それを通知・再開の経路として扱う。二重通知は許容し、重複排除の有無を開始条件にしない。上記の調査・準備を行っても必要な接続を確認できない場合は `Runtime-blocked` とし、調べた経路、確認できた能力、残る不足・未確認事項を報告してSidekickを起動しない。黙ってポーリング、別Lead、ユーザーの手動往復へ切り替えない。手動継続はユーザーが明示的に選んだ場合の別運用とする。

## 起動と通知

Leadは契約を定め、[ルーティング方針](routing-policy.md)に従って外部の許可済みプロファイルを解決する。使用ホストのモデル一覧でIDと対応エフォートを照合し、掲載されているだけで利用許可とみなさない。Sidekickへ[実行方針](sidekick-policy.md)と契約の全文を渡す。ツールの入力長制限で渡せない場合は内容を黙って切り詰めない。

タスク記録には `task_id`、試行、契約版、元LeadとSidekickのスレッド、書き込み担当を残す。Leadがターンを終える前に通知先と待機中のタスクを記録する。ホストの履歴・状態保存を利用できるなら、専用の制御ストアは不要。Sidekickは[引き渡し](../assets/handoff-template.md)に沿う構造化報告を残し、引き渡し対象への書き込みを止めてから、メッセージ送信機能で元Leadへ通知する。

実行中のLeadへのメッセージの扱いはホストに任せる。同じ報告が複数回来ても、既に確認済みなら読み飛ばしてよく、通知IDや一度だけの配送・起動を保証する仕組みは要求しない。Leadはタスクの現在状態に沿ってレビューし、古い試行やキャンセル済みタスクを採用しない。報告がない場合はSidekickの実行状態を確認し、異常終了や未完了を成功扱いしない。

元Leadのスレッドに新しい入力を始めるときは、その時点のLead設定を引き継ぐ。上書き指定を省略した場合の動作を確認し、ホストの継承機能を使う。委譲前に取得した古い設定を再指定して、待機中のユーザー変更を戻さない。Sidekick用のモデル・エフォートをLead再開の引数に流用しない。同じ履歴を別App Serverへforkするだけでは、元Leadの再開と扱わない。純待機中はLeadへの定期入力を発生させず、通信維持と障害検知を通常のプログラムに任せる。

`Waiting for sidekick`、`Ready for review`、`Accepted`、`Runtime-blocked` はこのSkillの業務状態であり、Codex公式APIの状態名ではない。`Runtime-ready` は必要な能力と元スレッドへの接続を確認できた状態とする。確認には現行仕様、読み取り応答、有効な既存の検証結果を使い、毎回の独立した通知・再開試験を開始条件にしない。実際の通知・再開をまだ試していなければその旨を記録し、実証済みとは報告しない。
