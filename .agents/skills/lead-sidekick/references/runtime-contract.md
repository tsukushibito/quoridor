# 実行基盤との契約

このSkillは委譲と受入れの判断を定める。スレッドの起動、通知配送、再開、重複防止、永続化は、そのセッションを管理するホストの実機能に接続する。特定版のApp Server、ソケット位置、独自の常駐プロセスをSkillの前提にしない。

## 毎回の能力確認

利用中のホストが公開するツールと、そのホストで実際に動くApp Serverのスキーマを確認する。CLIと稼働中サーバーが同じ版とは仮定しない。メソッド名や引数は過去の会話やこの文書から推測せず、現行スキーマまたは公式資料と照合する。

| 能力 | 確認すること |
|---|---|
| Lead識別 | 元のホストとLeadスレッドIDを信頼できる情報から取得できる |
| 設定保持 | Leadの実効モデル・エフォートをホストから確認でき、Sidekick用設定と分離できる |
| Sidekick起動 | 許可済みモデルとエフォート、Sidekick方針、今回の契約を省略せず渡せる |
| 通知と再開 | Lead終了後も生きる経路で報告を受け、元のスレッドへ必要時だけ入力できる |
| 状態と所有権 | Leadの実行中・別作業中・キャンセル済み状態と、Sidekickの書き込み停止を確認できる |
| 永続化と異常検知 | 未配送報告、試行、受入状態を保持し、報告前の異常終了を成功と区別できる |
| 計測 | 取得可能な使用量と時刻をLeadへの定期的なモデル入力なしで記録できる |

たとえばApp Serverに既存スレッドへの入力機能があっても、それだけで通知配送、異常検知、元ホストでの再開まで成立したとは扱わない。接続が揃わない場合は `Runtime-blocked` と不足能力を報告し、Sidekickを起動しない。黙ってポーリング、別Lead、ユーザーの手動往復へ切り替えない。手動継続はユーザーが明示的に選んだ場合の別運用とする。

## 起動と通知

Leadは契約を定め、[ルーティング方針](routing-policy.md)に従って外部の許可済みプロファイルを解決する。使用ホストのモデル一覧でIDと対応エフォートを照合し、掲載されているだけで利用許可とみなさない。Sidekickへ[実行方針](sidekick-policy.md)と契約の全文を渡す。ツールの入力長制限で渡せない場合は内容を黙って切り詰めない。

実行基盤は `task_id`、試行、契約版、元LeadとSidekickのスレッド、通知ID、書き込み担当を関連付ける。Leadがターンを終える前に通知待ち状態を保存する。Sidekickは[引き渡し](../assets/handoff-template.md)に沿う構造化報告を保存し、引き渡し対象への書き込みを止めてから通知する。

配送側は通知が先着した場合に保留し、Leadが実行中・別作業中なら無条件に割り込まない。明示通知とターン終了イベントによる二重起動・二重集計を防ぐ。古い試行、再配送、キャンセル済みタスクを採用しない。通知前の異常終了や報告なしの正常終了も検知する。結果不明の送信は状態と相関情報で照合し、確認できないexactly-once保証や無制限再送を設けない。

元Leadのスレッドに新しい入力を始めるときは、その時点のLead設定を引き継ぐ。Sidekick用のモデル・エフォートをLead再開の引数に流用しない。同じ履歴を別App Serverへforkするだけでは、元Leadの再開と扱わない。純待機中はLeadへの定期入力を発生させず、通信維持と障害検知を通常のプログラムに任せる。

`Waiting for sidekick`、`Ready for review`、`Accepted`、`Runtime-blocked` はこのSkillの業務状態であり、Codex公式APIの状態名ではない。実ホストでSidekick起動、ターン終了後の通知、元Leadの一度の再開、Lead設定の保持、純待機中のモデル呼び出しゼロを確認するまでは `Runtime-ready` と報告しない。
